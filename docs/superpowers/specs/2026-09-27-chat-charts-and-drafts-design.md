# Графіки в чаті та чернетки транзакцій — дизайн

Дата: 2026-09-27. Гілка: `feature/chat-agent`. Базується на чинному чат-агенті (`backend/agent/`, `routers/chat.py`, `ChatWidget.vue`).

## Мета

1. Асистент малює графік у чаті за запитом користувача («покажи витрати на таксі й каву по місяцях за пів року»).
2. Асистент готує транзакцію з тексту («запиши, що я витратив 300 на таксі вчора»). Користувач перевіряє чернетку і сам її додає.

## Рішення

| # | Рішення |
|---|---|
| D1 | Запис **тільки після підтвердження користувачем**. Агент не має інструменту запису. Він повертає чернетку, а запис робить наявний `POST /transactions` з фронтенду, коли користувач натискає кнопку. |
| D2 | У першому випуску є тільки **додавання транзакції**. Бюджети, редагування й видалення не входять. |
| D3 | Чернетка — **картка-форма, яку можна змінити**: тип, сума, дата, категорія (select), опис. Валюта UAH, `is_fop` береться з профілю. Курс і валюту в картці не показуємо. |
| D4 | Графіки будуються за **структурованим запитом** (без SQL): модель заповнює обмежену схему, бекенд валідує її, вибирає дані наявним хендлером `get_transactions` з `current_user_id` з токена і агрегує в Python. Цифри на графіку ніколи не пише LLM. |
| D5 | Великі дані йдуть у полі **`attachments`** відповіді `/chat/`, а не в LLM. Модель отримує коротке зведення. Назад у LLM іде тільки текст повідомлень. |

## Архітектура

```
LLM ──tool call──▶ build_chart / propose_transaction (agent/tools.py)
                     │ agent/charts.py (валідація + агрегація, чисті функції)
                     │ agent/drafts.py (валідація чернетки, чисті функції)
                     ▼
        WithAttachment(model_result, attachment)
                     │
runner.run_tool ─────┼── model_result (JSON) ──▶ LLM
                     └── attachment ──▶ AgentResult.attachments ──▶ ChatResponse.attachments
                                                                        │
ChatWidget ◀────────────────────────────────────────────────────────────┘
  ├─ type "chart"             → ChatChart.vue (vue-chartjs: Bar / Line / Doughnut)
  └─ type "transaction_draft" → TransactionDraftCard.vue → api.createTransaction → POST /transactions
```

### Контракт `build_chart` (аргументи моделі)

| Поле | Значення | Обов'язкове |
|---|---|---|
| `chart` | `bar` \| `line` \| `doughnut` | так |
| `group_by` | `category` \| `day` \| `week` \| `month` | так |
| `start_date`, `end_date` | `YYYY-MM-DD`, start ≤ end, період ≤ 731 день | так |
| `type` | `expense` \| `income` \| `both` (типово `expense`) | ні |
| `metric` | `sum` \| `count` (типово `sum`) | ні |
| `categories` | список назв категорій (≤ 12), без урахування регістру | ні |
| `search` | текст для пошуку в описі | ні |
| `title` | заголовок графіка (≤ 80 символів) | ні |

Правила:
- `doughnut` можна лише з `group_by="category"` і `type` ≠ `both`.
- Невідомі назви категорій дають помилку аргументу зі списком доступних категорій (до 30).
- Вибірка: `get_transactions(limit=501)`. Якщо транзакцій більше за 500, модель отримує помилку «звузьте період або фільтри».
- **`group_by="category"`:** мітки — назви категорій, відсортовані за спаданням. Показуємо 11 перших, решта йде в «Інше». Серії: `both` дає «Доходи» і «Витрати», інакше одна серія.
- **`group_by` за часом:** безперервні мітки від start до end з нулями. `day` → `YYYY-MM-DD`, `week` → дата понеділка `YYYY-MM-DD`, `month` → `YYYY-MM`.
  - Якщо задано `categories`, будується по серії на кожну категорію.
  - Інакше `both` дає «Доходи» і «Витрати», а решта типів — одну серію.
- `sum` рахується за `transaction_amount` (UAH) з округленням до 2 знаків, `count` — за кількістю записів.
- Вкладення: `{"type": "chart", "chart": {"chart", "title", "labels", "datasets": [{"label", "data"}], "unit": "грн"|"шт", "start_date", "end_date"}}`.
- Модель отримує: `{"status": "chart_shown", "labels": N, "series": [{"label", "total"}], "unit"}`.

### Контракт `propose_transaction`

| Поле | Правило |
|---|---|
| `type` | `income` \| `expense` |
| `amount` | число, 0 < amount ≤ 10 000 000, округлення до 2 знаків |
| `date` | `YYYY-MM-DD`, не пізніше сьогодні і не раніше ніж 5 років тому |
| `category` | назва (необов'язково). Шукаємо без урахування регістру серед категорій потрібного типу. Якщо не знайдено: `category_id = null`, у картці порожній select і підказка |
| `description` | ≤ 255 символів (необов'язково) |

- Вкладення: `{"type": "transaction_draft", "draft": {"type", "amount", "currency": "UAH", "date", "category_id", "category_name", "description", "is_fop"}}`. `is_fop` береться з `get_categories()["user_is_fop"]`.
- Модель отримує: `{"status": "draft_shown", "note": "…додасться лише після підтвердження…", "draft": {...}}`.

### Runner і API

- `tools.run_tool(name, arguments, user_id) -> (content: str, attachment: Optional[dict])`. `execute_tool` залишається обгорткою, яка повертає тільки `content`.
- Runner збирає не більше **3 вкладень** на відповідь. Для зайвих tool отримує `{"error": "Забагато графіків або чернеток в одній відповіді"}`.
- `AgentResult.attachments: list`. `ChatResponse.attachments: List[dict]` (типово `[]`).
- Системний промпт: правило 6 уточнено («не змінюєш дані сам, транзакцію лише пропонуєш через `propose_transaction`»), додано правила про `build_chart`: не дублювати в тексті всі цифри графіка і не казати «додано» про чернетку.

### Фронтенд

- Повідомлення асистента зберігає `attachments`. У `payload` до `/chat/` ідуть лише `{role, content}`.
- `ChatChart.vue`: vue-chartjs (`Bar`, `Line`, `Doughnut`), реєстрація потрібних елементів Chart.js, фіксована палітра, висота 220px, заголовок, одиниця в tooltip.
- `TransactionDraftCard.vue` має 4 стани: `editing` → `saving` → `saved` («✓ Додано») | `cancelled` («Скасовано»); помилка показується в картці.
  - Категорії беруться з `transactionStore.categories[form.type]`. Якщо їх немає, спершу викликається `fetchCategories()`.
  - Кнопка «Додати» викликає `api.createTransaction({type, amount, date, category_id, description, currency: 'UAH', is_fop})`, а потім окремо `transactionStore.fetchTransactions()`, щоб оновити дашборд. Помилка оновлення не показується як помилка запису, інакше користувач може додати дубль.
  - Кнопка неактивна, поки не заповнено суму, дату й тип.

## Обробка помилок

- **Некоректні аргументи моделі:** модель отримує `{"error": ...}` з поясненням (наявний механізм `ToolArgumentError`) і може спробувати ще раз.
- **Помилка при збереженні картки:** рядок `detail` з відповіді (400/422) показується в картці. Інакше показується загальне повідомлення «Не вдалося додати транзакцію». Глобальний toast показується як завжди (URL не `/chat`).

## Тестування

- `charts.py`: юніт-тести агрегації (кожен `group_by`, `both`, `count`, «Інше», заповнення нулями, тижні, межі валідації).
- `drafts.py`: юніт-тести валідації (межі суми й дати, пошук категорії, невідома категорія).
- tools: `build_chart` і `propose_transaction` повертають `WithAttachment`, передають `current_user_id`, перевищення 500 дає помилку, невідомі категорії теж дають помилку. `run_tool` віддає вкладення.
- runner: вкладення збираються, ліміт 3 працює, `execute_tool`-сумісність не зламана.
- router: `attachments` є у відповіді, типово `[]`.
- Фронтенд: збірка `vite build`, ручна перевірка (графік, картка: додати, скасувати, помилка).
