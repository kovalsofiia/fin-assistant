# Методологія пілотного експерименту

Документ описує методологію, за якою побудовано пілотний харнес (`research/llm_test_harness/`)
і зібрано результати в [03-pilot-results.md](03-pilot-results.md). Він відповідає завданням 2
теми кваліфікаційної роботи: формалізувати критерії порівняння моделей і підготувати дані
для експерименту, в обсязі, придатному для звіту з виробничої практики.

## 1. Об'єкт тестування (задача)

Пілот бере одну задачу: **згенерувати pytest-тести для модуля `backend/agent/drafts.py`**
(валідація чернетки транзакції, яку пропонує чат-агент fin-assistant). Модуль обрано з таких
причин:

- **Чисті функції без побічних ефектів.** Немає мережі, БД чи файлової системи — тести
  виконуються миттєво й детерміновано, а різниця в результатах пояснюється лише якістю
  згенерованих тестів, а не флакі-інфраструктурою.
- **Помірна складність:** 44 інструкції, 18 гілок (`coverage.py`), 2 публічні функції
  (`build_draft`, `draft_model_result`), одна незвична деталь API — `today: date` є
  **обов'язковим** параметром (для детермінованості тестів дата «сьогодні» ін'єктується
  ззовні, а не читається з `date.today()` всередині функції).
- **Є еталон:** ручний набір `backend/tests/test_drafts.py` (16 тестів, 100% покриття) —
  baseline, з яким порівнюються згенеровані тести.

Модель отримує **лише вихідний код модуля** (без наявних тестів) і повертає файл тестів.
Це «холодна» генерація: перевіряється здатність моделі зрозуміти контракт функції з коду,
а не повторити побачені приклади.

## 2. Критерії оцінювання

| Критерій (з завдання кафедри) | Метрика в харнесі | Як рахується |
|---|---|---|
| Коректність тестів | **pass rate** | `passed / (passed + failed)`, або 0, якщо файл узагалі не збирається (`collection_error`) |
| Покриття коду | **line coverage, %** | `coverage.py --branch`, лише по `agent.drafts`, при незібраному файлі — не визначено |
| Здатність виявляти дефекти | **mutation score** | частка «вбитих» мутантів з фіксованого набору (розділ 4) |
| Стабільність результатів | **розмах між повторами** | різниця max−min тієї самої метрики за `REPEATS_PER_MODEL` незалежних генерацій з тим самим промптом |
| Час виконання | **latency, с** | час одного запиту до API (генерація тестів), окремо від виконання тестів (мілісекунди, неважливо) |
| Обчислювальні витрати | **вартість, $** | `prompt_tokens/1e6 × ціна_входу + completion_tokens/1e6 × ціна_виходу`, ціни — з `config.py` (OpenRouter, 2026-09-27) |

**Важлива методологічна умова:** mutation score рахується **лише** для файлів, що повністю
проходять (`pass_rate == 1.0`) проти оригінального модуля. Якщо тести не збираються або
хибно падають на правильному коді, вони так само «падають» на кожному мутанті — це не
виявлення дефектів, а шум, і mutation score в такому разі не визначено (`None`), а не `1.0`.
Це вимога стандартної практики mutation testing (спершу «зелений» набір тестів, потім
ін'єкція дефектів) — під час пілоту харнес спершу порушував це правило, дефект знайдено
й виправлено до збору фінальних даних (див. `research/llm_test_harness/test_harness_unit.py`,
тести `test_broken_test_file_skips_mutation_scoring_instead_of_inflating_it` і
`test_always_failing_test_file_also_skips_mutation_scoring`).

## 3. Однакові умови для всіх моделей

- **Один промпт** (`prompts.py`), той самий текст і порядок вимог для кожної моделі й повтору.
- **temperature = 0.2** — для більш детермінованої, «інженерної» відповіді.
- **Без tool calling й агентного циклу** — один запит, одна відповідь, щоб ізолювати саме
  здатність генерувати тести від впливу агентної інфраструктури.
- **`REPEATS_PER_MODEL = 2`** незалежних генерації на модель — мінімум, придатний лише для
  виявлення нестабільності «в принципі»; для статистично значущих висновків основний етап
  диплому має використати 3–5 повторів. (Для Claude Sonnet 5 в результатах фактично 3
  прогони — технічна деталь запуску, не зміна параметра; див.
  [03-pilot-results.md](03-pilot-results.md#виправлена-методологічна-помилка-фоновий-запуск-і-хибний-висновок-про-deepseek).)
- **6 моделей-кандидатів** (`config.PILOT_MODELS`): дешеві — Gemini 3.5 Flash Lite,
  GPT-5.6 Luna, DeepSeek V4 Flash; флагманські — Claude Sonnet 5, GPT-5.6 Terra, Grok 4.6.
  Список можна запускати вибірково: `run_pilot.py <підрядок назви> ...`.
- **Важливо: скрипт слід запускати в передньому плані**, не як фоновий/відв'язаний процес
  — у середовищі розробки, де готувався цей пілот, фонові мережеві виклики ставали
  аномально повільними (див. знахідку в `03-pilot-results.md`).
- **Доступ до моделей:** один API — OpenRouter, той самий клієнт (`openai` SDK з `base_url`),
  щоб відмінності пояснювалися моделями, а не способом доступу.

## 4. Мутаційне тестування: 7 ручних мутантів

Замість `mutmut` (повний перебір усіх можливих мутацій, довше й складніше пояснити в звіті)
пілот використовує **7 вручну сконструйованих мутантів** `agent/drafts.py`
(`research/llm_test_harness/mutants.py`) — кожен імітує типову реальну помилку:

| ID | Що змінено |
|---|---|
| `m1_today_boundary` | `day > today` → `day >= today` (сьогоднішня дата хибно відхиляється) |
| `m2_amount_boundary` | нижня межа суми `>` → `>=` (дозволяє суму = мінімуму) |
| `m3_no_rounding` | забрано округлення суми до 2 знаків |
| `m4_max_past_days` | ліміт «5 років» помилково стає «6 років» |
| `m5_is_fop_not_bool` | забрано приведення `is_fop` до `bool` |
| `m6_description_off_by_one` | обрізання опису на символ коротше за ліміт |
| `m7_category_case_sensitive` | пошук категорії стає чутливим до регістру |

Кожен мутант — точкова текстова заміна в оригінальному коді (перевірено: застосовується
рівно один раз і компілюється). Еталонний набір тестів `test_drafts.py` «вбиває» 6 із 7
(не ловить `m5`, бо жоден ручний тест не передає `is_fop` як нетипове значення) — це
задає верхню орієнтовну межу для порівняння з LLM-згенерованими наборами.

## 5. Пісочниця виконання

Кожен запуск тестів відбувається в ізольованому тимчасовому пакеті:
`{agent/__init__.py, agent/drafts.py, core/__init__.py, core/constants.py, tests/test_generated.py}`
— мінімальний набір без FastAPI/Supabase/openai, тож виконання відбувається без мережі й
за мілісекунди. Для мутаційного тестування в `agent/drafts.py` пісочниці підставляється
мутований текст замість оригінального.

## 6. Обмеження пілоту

- **N = 2 повтори на модель** — недостатньо для строгих статистичних висновків
  (довірчих інтервалів тощо); підходить лише для демонстрації методу й перших спостережень.
- **Одна задача (один модуль).** Основний етап диплому має розширити набір задач: кілька
  модулів різної складності, різні типи тестового завдання (unit-тести, тестові дані,
  пошук дефектів у вже написаному коді) — саме це й вимагає завдання 2 диплому.
- **Харнес слід запускати в передньому плані.** Перша спроба запустити його як фоновий
  процес дала хибне враження «зависання» одного провайдера — насправді причина була в
  середовищі виконання, а не в моделі; див.
  [03-pilot-results.md](03-pilot-results.md#виправлена-методологічна-помилка-фоновий-запуск-і-хибний-висновок-про-deepseek).
- **Мутаційне тестування — 7 ручних мутантів**, не повний `mutmut`-прогін; для основного
  етапу варто розглянути `mutmut` або `cosmic-ray` для ширшого й менш суб'єктивного набору.
