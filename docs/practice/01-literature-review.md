# Огляд літератури: застосування великих мовних моделей (LLM) для автоматизованого тестування програмного забезпечення

Автоматизоване тестування традиційно спирається на детерміновані техніки — пошуково-орієнтоване тестування (search-based software testing, SBST), символьне виконання, fuzzing. Поява великих мовних моделей (LLM), здатних генерувати синтаксично й семантично коректний код, відкрила новий напрям досліджень: використання LLM для генерації unit-тестів, аналізу коду, побудови тестових даних та навіть оцінювання якості самих тестів. Нижче систематизовано ключові підходи, реальні інструменти, бенчмарки та метрики, що використовуються в актуальній науковій літературі та індустріальних звітах.

## 1. Генерація unit-тестів за допомогою LLM

Дослідники виокремлюють кілька архітектурних підходів до генерації тестів LLM: few-shot prompting з контекстом функції (сигнатура, docstring, приклади використання), fine-tuning моделі на парах "код–тест", retrieval-augmented generation (RAG) над кодовою базою для підбору релевантних фрагментів та типів, а також агентні цикли, у яких LLM генерує тест, виконує його, аналізує помилку компіляції чи падіння і повторно уточнює запит.

Показовим прикладом few-shot підходу з адаптивним зворотним зв'язком є **TestPilot** (Meta) — система, що вбудовує в промпт сигнатуру функції, документацію, приклади використання з проєктної документації та вихідний код, а у разі падіння згенерованого тесту формує новий промпт із текстом помилки, щоб модель виправила тест. На вибірці з 25 npm-пакетів (1684 API-функції) TestPilot з gpt-3.5-turbo досяг медіанного покриття операторів 70,2% та покриття гілок 52,8%, суттєво перевершивши попередню техніку Nessie ([An Empirical Evaluation of Using Large Language Models for Automated Unit Test Generation](https://arxiv.org/abs/2302.06527)).

Іншим напрямом є не генерація тестів "з нуля", а *покращення* вже наявних людських тестів. **TestGen-LLM**, розроблений у Meta, доповнює існуючі тестові класи новими тестовими випадками, пропускаючи їх через фільтри, що гарантують вимірюване покращення (компільованість, стабільний прохід, приріст покриття) і виключають регресії від "галюцинацій" моделі. У продуктивному застосуванні на Instagram Reels/Stories 75% згенерованих тестів успішно компілювались, 57% стабільно проходили, а 25% збільшували покриття; під час внутрішніх "test-a-thon" 73% рекомендацій системи були прийняті інженерами у продакшн ([Automated Unit Test Improvement using Large Language Models at Meta](https://arxiv.org/abs/2402.09171)). Відкриту реалізацію подібного підходу, натхненну TestGen-LLM, реалізовано у проєкті **Cover-Agent (Qodo/CodiumAI)** ([We created the first open-source implementation of Meta's TestGen-LLM](https://www.qodo.ai/blog/we-created-the-first-open-source-implementation-of-metas-testgen-llm/)).

Гібридний підхід, що поєднує SBST з LLM, реалізовано у **CodaMosa** (Lemieux, Inala, Lahiri, Sen, ICSE 2023): коли еволюційний пошук (наприклад, Pynguin) виходить на "плато" покриття, система звертається до Codex за прикладами тестів для недопокритих функцій, після чого пошук продовжується з новими орієнтирами. На вибірці з 486 бенчмарків CodaMosa статистично значуще перевершив як чисто пошукові, так і чисто LLM-базовані підходи за покриттям ([CodaMosa: Escaping Coverage Plateaus in Test Generation with Pre-Trained Large Language Models, ICSE 2023](https://dl.acm.org/doi/10.1109/ICSE48619.2023.00085)). Для екосистеми Python подібну ідею високопокривної генерації тестів реалізує **CoverUp**, що ітеративно аналізує звіти про покриття та спрямовує LLM на непокриті ділянки коду ([CoverUp: Effective High Coverage Test Generation for Python](https://arxiv.org/pdf/2403.16218)). Нарешті, повністю агентні цикли з виконанням і зворотним зв'язком представлені у **TestForge**, який використовує помилки компіляції, падіння виконання та непокриті сегменти коду як частину ітеративного агентного циклу для генерації тестів у великих файлах реальних кодових баз ([TestForge: Feedback-Driven, Agentic Test Suite Generation](https://arxiv.org/abs/2503.14713)).

## 2. Аналіз коду великими мовними моделями для завдань, релевантних тестуванню

Здатність LLM "розуміти" код лежить в основі не лише генерації тестів, а й суміжних задач — локалізації дефектів (bug/fault localization) та допомоги в статичному аналізі. Емпіричні дослідження показують, що GPT-подібні моделі здатні виконувати локалізацію дефектів на рівні операторів без виконання коду ("test-free fault localization"), використовуючи лише семантичне розуміння структури програми та опис помилки ([Large Language Models for Test-Free Fault Localization](https://arxiv.org/pdf/2310.01726)). Систематичне порівняльне дослідження оцінює сучасні моделі (Qwen2.5-Coder-32B-Instruct, DeepSeek-V3, GPT-4.1 mini, Gemini-2.5-Flash) на задачах локалізації дефектів на рівні операторів, використовуючи HumanEval-Java та Defects4J як тестові набори ([Large Language Models for Fault Localization: An Empirical Study](https://arxiv.org/abs/2510.20521)). Загальний огляд застосувань LLM у програмній інженерії, включно з локалізацією дефектів, автоматичним ремонтом програм (APR) та статичним аналізом, систематизовано у великому оглядовому дослідженні ([A Survey on Large Language Models for Software Engineering](https://arxiv.org/pdf/2312.15223)).

## 3. Формування тестових даних (test data / fixture generation) LLM-ами

Окремий напрям — генерація не самого тестового коду, а вхідних даних і фікстур, необхідних для реалістичного тестування. Огляд підходів до синтетичної генерації даних LLM-ами описує промпт-орієнтоване augmentation, RAG-підходи та self-instruct методи для отримання структурованих та текстових наборів даних ([Synthetic Data Generation Using Large Language Models: Advances in Text and Code](https://arxiv.org/abs/2503.14023)). Для табличних тестових даних промислового рівня запропоновано **FASTGEN** — систему, яка за метаданими про схему й обмеження виводить розподіл та генерує скрипти семплування для отримання наборів довільного розміру, що придатно для наповнення тестових середовищ і БД без ручного написання фікстур ([FASTGEN: Fast and Cost-Effective Synthetic Tabular Data Generation with LLMs](https://arxiv.org/pdf/2507.15839)). Ширший огляд процесів генерації, курації та оцінювання синтетичних даних, зокрема застосовних до формування тестових наборів, наведено у ([On LLMs-Driven Synthetic Data Generation, Curation, and Evaluation: A Survey](https://arxiv.org/pdf/2406.15126)).

## 4. Виявлення дефектів LLM: LLM-as-detector, LLM-суддя та mutation testing

LLM дедалі частіше застосовують не лише як генератор коду/тестів, а й як "суддю" (LLM-as-a-judge), що оцінює якість чужого коду чи тестів за критеріями коректності, читабельності та відповідності вимогам. Комплексний огляд систематизує методи LLM-суддів для оцінювання генерації коду, зазначаючи, що великі закриті моделі (наприклад, GPT-4-turbo) є найнадійнішими суддями, тоді як менші відкриті моделі часто помилково класифікують некоректний код як правильний ([LLMs-as-Judges: A Comprehensive Survey on LLM-based Evaluation Methods](https://arxiv.org/pdf/2412.05579)). Спеціалізований бенчмарк **CodeJudgeBench** зіставляє пари "хороших/поганих" відповідей саме для трьох задач — генерації коду, виправлення коду та генерації unit-тестів — що робить його безпосередньо релевантним оцінюванню тестів LLM-суддею ([CodeJudgeBench: Benchmarking LLM-as-a-Judge for Coding Tasks](https://arxiv.org/pdf/2507.10535)).

Паралельно з "суддівством" ключовим інструментом об'єктивної оцінки якості згенерованих тестів є mutation testing: у вихідний код вносяться штучні дефекти (мутанти), і якість тестового набору вимірюється часткою "вбитих" мутантів (mutation score). Дослідження показує, що покриття коду є слабким індикатором здатності тестів виявляти дефекти — траплялися тестові набори зі 100% покриттям, але лише 4% mutation score, тоді як mutation score є суттєво надійнішою і суворішою метрикою ([A Comprehensive Study on Large Language Models for Mutation Testing](https://arxiv.org/pdf/2406.09843); [Do Coverage and Mutation Scores of LLM-Generated Test Suites Correlate with Their Effectiveness?](https://arxiv.org/abs/2607.22880)). Підхід **MutGen**, що використовує LLM безпосередньо для mutation-guided генерації тестів, досяг mutation score 89,5% та 89,1% на HumanEval-Java та Leetcode-Java відповідно, перевершивши EvoSuite та наївний prompting з Llama-3.3 ([Mutation-Guided Unit Test Generation with a Large Language Model](https://arxiv.org/abs/2506.02954)).

## 5. Бенчмарки та методології оцінювання

Фундаментальним бенчмарком для оцінки здатності LLM генерувати функціонально коректний код є **HumanEval**, представлений разом з моделлю Codex: 164 завдання типу "docstring → функція", а якість вимірюється метрикою pass@k. Codex вирішував 28,8% завдань з одним семплом і до 70,2% за 100 семплах на завдання, тоді як GPT-3 без файнтюну на коді — 0% ([Evaluating Large Language Models Trained on Code](https://arxiv.org/abs/2107.03374)). Для оцінки на рівні класів (а не окремих функцій) розроблено **ClassEval** — 100 вручну складених Python-завдань класового рівня; дослідження показало, що всі протестовані LLM значно гірше справляються з класовим кодом порівняно з методним рівнем HumanEval, і що GPT-4/GPT-3.5 домінують над іншими моделями саме на цьому типі задач ([ClassEval: A Manually-Crafted Benchmark for Evaluating LLMs on Class-level Code Generation](https://arxiv.org/abs/2308.01861)).

Для оцінки на рівні реальних інженерних задач (виправлення issue в реальних GitHub-репозиторіях) використовується **SWE-bench** — 2294 завдання з 12 Python-репозиторіїв, а також похідні варіанти SWE-bench Lite та SWE-bench Verified для зменшення шуму й підвищення надійності оцінки ([SWE-Bench+: Enhanced Coding Benchmark for LLMs](https://arxiv.org/abs/2410.06992)). Безпосередньо для генерації тестів створено **TestGenEval** (Meta AI, Jain, Synnaeve, Rozière, 2024) — 68 647 тестів з 1210 пар "код–тест" у 11 реальних Python-репозиторіях, що охоплює як завершення окремих тестів, так і генерацію повного тестового файлу; на відміну від попередніх бенчмарків (TestEval, SWT-Bench), TestGenEval повідомляє mutation score поряд із покриттям і вимагає, щоб тести відрізняли коректний код від коду зі внесеними синтетичними дефектами ([TestGenEval: A Real World Unit Test Generation and Test Completion Benchmark](https://arxiv.org/abs/2410.00752)).

Джерелом реальних, відтворюваних дефектів для експериментів з mutation testing, автоматичного ремонту програм (APR) та генерації регресійних тестів слугує **Defects4J** — куратована колекція із 835 реальних багів (версія 2.1.0) з 17 великих Java-проєктів, кожен з парою "буг/фікс" і повним тестовим набором ([Defects4J: a database of existing faults to enable controlled testing studies for Java programs, ISSTA 2014](https://dl.acm.org/doi/10.1145/2610384.2628055)). Порівняльне дослідження генерації тестів на основі моделей показало, що серед п'яти сучасних LLM моделі Anthropic Claude демонстрували найбільш надійну й стабільну продуктивність за різних стратегій генерації ([An Empirical Evaluation of Using Large Language Models for Automated Model-Based Test Generation](https://arxiv.org/pdf/2608.27094)).

## 6. Метрики якості згенерованих тестів

У проаналізованій літературі практика оцінювання LLM-генерованих тестів спирається на комбінацію кількох метрик, оскільки жодна з них окремо не є достатньою. **Correctness / pass rate** (наприклад, pass@1, pass@5) вимірює частку тестів, що компілюються і стабільно проходять — саме ця метрика лежить в основі HumanEval (pass@k) і використовується в TestGenEval для обох задач генерації ([Evaluating Large Language Models Trained on Code](https://arxiv.org/abs/2107.03374); [TestGenEval](https://arxiv.org/abs/2410.00752)). **Покриття коду** (рядкове/гіллясте, line/branch coverage) є найпоширенішою метрикою в роботах з генерації тестів — застосовується в TestPilot (медіанне покриття операторів і гілок) та в TestGen-LLM (частка тестів, що збільшують покриття) ([TestPilot](https://arxiv.org/abs/2302.06527); [TestGen-LLM](https://arxiv.org/abs/2402.09171)). **Mutation score** визнається суттєво надійнішою мірою здатності тестів виявляти дефекти, ніж саме лише покриття, і тому включена як окрема метрика в TestGenEval і в спеціалізовані дослідження mutation testing з LLM ([TestGenEval](https://arxiv.org/abs/2410.00752); [Do Coverage and Mutation Scores of LLM-Generated Test Suites Correlate with Their Effectiveness?](https://arxiv.org/abs/2607.22880)). Стабільність і детермінованість тестів при повторних запусках (відсутність "флейкі"-поведінки) є частиною фільтрів TestGen-LLM, які вимагають, щоб тест "стабільно проходив" (passed reliably) при повторному виконанні, перш ніж вважатися прийнятним ([TestGen-LLM](https://arxiv.org/abs/2402.09171)). Час виконання та обчислювальна/токенова вартість генерації враховуються, зокрема, у дослідженні, що аналізує ефективність по токенах поряд із якістю тестів ([Code Health in LLM-Based Test Generation: Effectiveness and Token Efficiency](https://arxiv.org/pdf/2608.18645)), а також фігурують як практичний компроміс "якість/вартість" у роботах з агентною генерацією тестів, де кількість викликів моделі й ітерацій зворотного зв'язку безпосередньо впливає на витрати ([TestForge: Feedback-Driven, Agentic Test Suite Generation](https://arxiv.org/abs/2503.14713)).

## Огляд моделей-кандидатів

У розглянутій літературі та порівняльних дослідженнях для оцінки здатності до генерації тестів і аналізу коду типово залучають декілька родин моделей. **OpenAI GPT** (GPT-3.5/GPT-4/GPT-4-turbo, а також кодова похідна Codex) — історично перша модель, на якій побудовано HumanEval і TestPilot, і досі є базовою точкою порівняння в більшості бенчмарків ([Evaluating Large Language Models Trained on Code](https://arxiv.org/abs/2107.03374)). **Anthropic Claude** (зокрема Claude 3) регулярно включають у порівняльні дослідження через стабільність і надійність відповідей: в одному з досліджень моделі Claude показали найбільш консистентну продуктивність серед п'яти протестованих LLM для генерації тестів на основі моделей ([An Empirical Evaluation of Using Large Language Models for Automated Model-Based Test Generation](https://arxiv.org/pdf/2608.27094)), а великі закриті моделі на кшталт GPT-4-turbo і Claude 3 також фігурують як типові "судді" в LLM-as-a-judge дослідженнях ([LLMs-as-Judges: A Comprehensive Survey](https://arxiv.org/pdf/2412.05579)). **Google Gemini** включають у ці ж порівняння як третього гравця серед провідних закритих моделей (наприклад, Gemini-2.5-Flash у дослідженнях локалізації дефектів) ([Large Language Models for Fault Localization: An Empirical Study](https://arxiv.org/abs/2510.20521)). Нарешті, відкриті кодові моделі **DeepSeek-Coder / DeepSeek-Coder-V2** та **Qwen2.5-Coder** залучають як представників відкритої альтернативи закритим API-моделям: Qwen2.5-Coder-32B демонструє найкращі результати серед відкритих моделей на HumanEval/MBPP, перевершуючи DeepSeek-Coder-V2-Lite вже у меншому 7B-розмірі, а DeepSeek-Coder-V2 демонструє 90,2% на HumanEval ([Qwen2.5-Coder Technical Report](https://arxiv.org/abs/2409.12186); [DeepSeek-Coder-V2](https://arxiv.org/pdf/2406.11931)). Такі моделі важливі для досліджень з відтворюваності та вартості, оскільки дозволяють локальне розгортання без залежності від комерційних API, що особливо актуально для експериментів з mutation testing та агентних циклів, які потребують великої кількості викликів моделі.
