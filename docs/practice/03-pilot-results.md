## Аналіз факторів

### Стабільність між повторами (Gemini): один й той самий промпт, дві різні поламки

Обидва запуски Gemini 3.5 Flash Lite взяли **той самий вхід** (однаковий модуль, `temperature=0.2`),
але дали протилежний результат:

- **Повтор 1 — найкращий результат пілоту.** 33 тести, 100% покриття (44/44 інструкції,
  18/18 гілок), **вбиває всі 7 мутантів — більше, ніж еталонний ручний набір** (6/7). Причина:
  модель явно перевірила `is_fop=1` (нетипове truthy-значення) і `assert result["is_fop"] is True`
  — саме цей випадок ловить мутант `m5_is_fop_not_bool`, якого не покриває жоден ручний тест
  `test_drafts.py`.
- **Повтор 2 — файл узагалі не запускається.** `NameError: name 'MAX_AMOUNT' is not defined`
  на рядку параметризації тесту: модель використала константу `MAX_AMOUNT` (побачену в
  вихідному коді) для межового значення, але **забула додати її в `from agent.drafts import ...`**.

Це пряма ілюстрація критерію «стабільність результатів»: та сама модель на тому самому
вході за одну генерацію показує найкращий результат пілоту, а за іншу — нульовий,
через технічну помилку одного рядка (пропущений імпорт), а не логічну.

### Спосіб формування запиту / характеристики моделі (GPT-5.6 Luna): систематична, не випадкова помилка

GPT-5.6 Luna провалила **100% тестів в обох повторах** (34 і 35 тестів), і обидва рази —
з **тією самою причиною**:

```python
def make_draft(**overrides):
    params = {
        "type": "expense",
        "amount": 100.0,
        "transaction_date": TODAY.isoformat(),
        "categories": CATEGORIES,
        "is_fop": False,
    }
    params.update(overrides)
    return build_draft(**params)
```

Спільна допоміжна функція для побудови тестових викликів **не передає обов'язковий
параметр `today`** — `TypeError: build_draft() missing 1 required positional argument: 'today'`
на кожному виклику. Це не одна забута дрібниця, а **той самий пропуск двічі, у двох незалежних
генераціях** — отже, це не випадковий флакі, а систематичне нерозуміння моделлю API з
обов'язковою ін'єкцією «поточної дати» замість звичного `date.today()` всередині функції.
Це узгоджується з пунктом завдання «фактори… спосіб формування запиту та характеристики
мовної моделі»: незвична (хоч і задокументована в docstring) сигнатура функції виявилась
пасткою саме для цієї моделі, тоді як Gemini (обидва повтори) правильно передала `today`.

Часткове покриття (17.7%) при 100% провалі пояснюється просто: `coverage.py` рахує рядки,
виконані **до** винятку — тіло `make_draft`/`build_draft` встигає виконатися частково
(валідація `type`) до того, як бракує `today` в сигнатурі виклику (сам виняток кидається
ще до входу в тіло функції — реальне покриття `agent/drafts.py` тут дає лише сам факт
імпорту модуля та обчислення значень за замовчуванням).

### Складність коду

Обидва фактори вище стосуються **не складності бізнес-логіки** (модуль малий, 44 інструкції),
а **складності контракту функції**: обов'язковий (без значення за замовчуванням) параметр
`today: date` і потреба явно імпортувати використані константи. Це узгоджується з очікуваною
гіпотезою диплому: складність задачі для LLM-генерації тестів визначається не лише розміром
коду, а й тим, наскільки «звичний» у нього API.

## Обмеження і технічна знахідка

**DeepSeek V4 Flash виключено з пілоту.** Перший виклик до цієї моделі через OpenRouter
завис на понад 10 хвилин без жодного винятку — ні per-request `timeout` в SDK `openai`,
ні навіть жорсткий тайм-аут на рівні `ThreadPoolExecutor.result(timeout=...)` (перевірено
окремо ізольованим тестом — сам механізм спрацьовує коректно за 2 секунди на звичайному
Python-коді) не перервали виклик. Це вказує на зависання нижче рівня Python — імовірно,
на етапі встановлення TCP-з'єднання чи DNS-резолюції, де без явного `httpx.Timeout` бібліотека
покладається на дефолтні (по суті необмежені для `connect`) тайм-аути. Харнес виправлено —
доданий явний `httpx.Client` з тайм-аутом на кожній фазі з'єднання (`connect=10s, read=60s`),
enforced на рівні сокета, а не потоку Python — але навіть після цього повторна спроба
достукатися до тієї самої моделі знову зависла без прогресу, тож для пілоту модель прибрано,
а виправлення лишається в коді (`run_pilot.py`) для основного етапу диплому.

**Практичний висновок для методології основного етапу:** інфраструктура порівняння LLM
має враховувати, що різні провайдери/моделі на тому самому API-шлюзі (OpenRouter) можуть
поводитися по-різному на мережевому рівні, а не лише в якості відповіді — це саме по собі
фактор «характеристики моделі/провайдера», який варто явно фіксувати в основному
дослідженні (наприклад, окрема метрика «частка успішних мережевих викликів» або
хардовий per-request timeout на рівні `httpx`, застосований з першого запуску).

висновки про те, яку LLM обирати для яких задач автоматизованого тестування.

## Рекомендації для основного етапу (з цього пілоту)

1. Збільшити `REPEATS_PER_MODEL` до 3–5: обидва спостереження пілоту (розкид Gemini,
   систематичність GPT-5.6 Luna) стали видимі лише завдяки повторам — з одним прогоном
   на модель жодного з цих фактів не побачити.
2. Додати явний `httpx.Timeout` з самого початку для всіх провайдерів (виправлення вже
   в `run_pilot.py`), і окрему метрику «мережева надійність виклику».
3. Розширити набір задач за межі одного модуля: щонайменше один модуль зі складнішим
   контрактом (більше гілок, зовнішні залежності через моки) і один — із навмисно
   «незвичною» сигнатурою, щоб цілеспрямовано перевірити фактор «спосіб формування API».
4. Розглянути `mutmut`/`cosmic-ray` для мутаційного тестування на основному етапі —
   7 ручних мутантів достатньо для пілоту, але не покривають простір мутацій системно.
